# Story 1.1 — Customer Signup & Login UI

You are working on the **Frontend** for **The Woven Cloud Kitchen**.

Implement the customer authentication UI using the existing frontend architecture, components, styling system, API layer, and coding conventions.

Before making changes, inspect the existing frontend codebase and understand:

* Project structure
* Existing routing
* Existing layout components
* Existing theme/design system
* Existing form components
* Existing input components
* Existing buttons
* Existing validation utilities
* Existing Redux store
* Existing RTK Query/API configuration
* Existing authentication state
* Existing notification/toast system
* Existing typography and spacing
* Existing responsive design patterns
* Existing SCSS/BEM conventions
* Existing reusable components

**Do not unnecessarily rewrite or restructure existing working code.**

Reuse existing components and utilities wherever possible.

Use strict TypeScript.

Do not use `any`.

---

# 1. Customer Signup Page

Create the customer signup page at:

```text
/signup
```

The page should allow a new customer to create an account.

## Signup Fields

The form must contain:

### Required

```text
Full Name
Mobile Number
Email
Password
Confirm Password
```

### Optional

```text
Alternate Mobile Number
Bio
```

### Consent

Include Terms & Conditions / Privacy Policy consent if this is already required by the application.

Example:

```text
☐ I agree to the Terms & Conditions and Privacy Policy
```

The signup button must remain disabled or prevent submission until required validation/consent requirements are satisfied.

---

# 2. Signup Form Validation

Use the project's existing validation approach.

If Zod is already available, use:

```text
Zod
+
React Hook Form
```

Do not introduce another validation library unnecessarily.

Validate:

### Name

* Required
* Trim whitespace
* Minimum reasonable length
* Maximum reasonable length

### Mobile Number

* Required
* Must be a valid phone number
* Must not be empty
* Must not be null
* Must not be undefined
* Should be normalized consistently before API submission

### Alternate Mobile Number

* Optional
* If provided, must be a valid phone number
* Must not be the same as the primary mobile number

### Email

* Required
* Valid email format
* Normalize email appropriately, such as trimming whitespace

### Password

* Required
* Follow the backend password policy
* Show appropriate validation messages

### Confirm Password

* Required
* Must match password

### Bio

* Optional
* Validate maximum length if backend defines one

---

# 3. Signup API Integration

Connect the form to:

```http
POST /api/auth/signup
```

Expected request structure:

```json
{
  "name": "Customer Name",
  "email": "customer@example.com",
  "phone": "9876543210",
  "alternatePhone": "9123456780",
  "password": "StrongPassword123",
  "bio": "Customer bio"
}
```

Do not send:

```text
role
isActive
_id
createdAt
updatedAt
```

The frontend must never allow the customer to select or submit:

```text
ADMIN
```

as a signup role.

The backend remains responsible for enforcing:

```text
role = CUSTOMER
```

---

# 4. Duplicate Email / Mobile Errors

Handle backend conflict responses properly.

Examples:

```text
Email already registered
Mobile number already registered
```

Display the error close to the relevant field where possible.

For example:

```text
Email
customer@example.com

Email already registered
```

and:

```text
Mobile Number
9876543210

Mobile number already registered
```

Do not display raw backend/database errors to the user.

Use the application's existing notification/toast system for general API errors if available.

---

# 5. Password Visibility

Implement password visibility controls for:

```text
Password
Confirm Password
```

Allow the user to toggle:

```text
Show password
Hide password
```

Use existing icon/button components if available.

The visibility toggle must not interfere with form validation.

# 6. Loading State

While signup is being submitted:

* Disable the submit button
* Show loading indicator
* Prevent duplicate submissions
* Keep entered form data intact
* Prevent accidental multiple API requests

Example:

```text
Creating Account...
```

After completion, restore the normal state.

---

# 7. Successful Signup

After successful signup:

Display an appropriate success message such as:

```text
Account created successfully.
Please login to continue.
```

Then redirect the customer to:

```text
/login
```

Unless the existing application authentication flow requires immediate login/token handling.

Follow the existing application architecture.

Do not invent a new authentication flow if one already exists.

# 14. Login API

Connect to:

```http
POST /api/auth/login
```

The API should receive:

```json
{
  "identifier": "customer@example.com",
  "password": "StrongPassword123"
}
```

The backend should determine whether the identifier is:

```text
Email
```

or:

```text
Primary phone
```

If the existing backend API instead expects a different request structure, inspect and follow the actual backend contract.

Do not modify the frontend API contract based on assumptions.

---

# 15. Login Error Handling

Handle:

```text
Invalid credentials
Account inactive
Account not found
Validation errors
Network errors
Server errors
```

Use user-friendly messages.

Example:

```text
Invalid email/mobile number or password.
```

Do not reveal sensitive authentication information unnecessarily.

Avoid messages such as:

```text
Email exists but password is wrong
```

when the backend follows a generic authentication error policy.

# 17. Successful Login

On successful login:

1. Receive JWT/token from backend.
2. Store authentication state using the application's existing authentication architecture.
3. Store user information safely.
4. Update Redux/auth state if Redux is already being used.
5. Redirect based on role.

Customer:

```text
/customer
```

or the existing customer home/dashboard route.

Admin:

```text
/admin
```

or the existing admin dashboard route.

Do not hardcode new dashboard routes if the application already defines them.

Example:

